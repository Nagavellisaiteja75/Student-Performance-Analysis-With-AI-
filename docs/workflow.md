# Documented Analytics Workflow

This document is the portfolio narrative for the project's end-to-end implementation. It can be used as a notebook plan, demo script, or internship submission appendix.

## 1. Business question

**Question:** Can historical student-context variables be used to estimate a final course grade early enough to support a constructive, human-led academic intervention?

**Decision-support objective:** Present an estimated grade range and a transparent support indicator to help educators decide whether to begin a student-centered conversation.

**Non-goals:** Predicting a student's worth, replacing staff judgement, ranking students, or automating consequential academic decisions.

## 2. Data collection

1. Run `python scripts/download_data.py`.
2. The script retrieves the official UCI archive and validates that it contains `student-mat.csv` and `student-por.csv`.
3. Raw files are stored locally in `data/raw/` and are excluded from version control.
4. Attribute the data source in reports and GitHub documentation.

## 3. Data understanding

The source comprises two files for Mathematics and Portuguese course performance. The project appends a `subject` field instead of joining the files. This preserves a clear course-record unit of analysis.

Use the generated `artifacts/data_profile.json` to answer:

- How many rows and columns are present after cleaning?
- How many records belong to each subject?
- Which fields contain missing values after validation?
- What is the distribution of the final-grade target (`G3`)?
- Which variables are numeric, categorical, and potential timing risks?

The UCI documentation identifies `G1`, `G2`, and `G3` as grade attributes. Since `G1` and `G2` occur before final grade `G3` and are strongly correlated with it, this project excludes them from the early-intervention feature set.

## 4. Cleaning and preparation

Run `python scripts/prepare_data.py`.

The preparation stage:

1. Combines the two files and adds `subject`.
2. Strips surrounding whitespace from textual values.
3. Coerces documented numeric fields to numeric data types.
4. Removes exact duplicate course records only.
5. Removes unusable target rows when `G3` is missing or outside the allowed 0–20 scale.
6. Leaves remaining feature-level missingness for imputation inside model training pipelines.

Why pipeline imputation matters: fitting an imputer before splitting train and test data lets test-distribution information leak into training. The project instead fits imputation and encoding within each model pipeline.

## 5. Exploratory data analysis

Run `python scripts/generate_eda.py`.

The project creates the following figures:

| Figure | Question it supports |
| --- | --- |
| Final-grade distribution | How are final grades distributed across course records? |
| Final grades by course | Do recorded grade distributions differ by subject? |
| Numeric correlation | Which numeric fields are associated in this sample? |

EDA should be narrated descriptively. Say “is associated with” rather than “causes.” Record the observations generated by your actual run; do not state a pattern that is not visible in the output.

## 6. Modeling and evaluation

Run `python scripts/train_models.py` or `python scripts/run_pipeline.py`.

### Feature design

- **Target:** `G3`, the final grade from 0 to 20.
- **Excluded:** `G3`, `G1`, and `G2`.
- **Numeric fields:** median-imputed and standardized.
- **Categorical fields:** most-frequent-imputed and one-hot encoded.

### Candidate models

1. Ridge Regression
2. Random Forest Regressor
3. Gradient Boosting Regressor

### Evaluation protocol

1. Make a reproducible 80/20 train/test split using `random_state=42`.
2. Compare candidates using five-fold cross-validation only on the training partition.
3. Choose the model with the lowest mean cross-validation MAE.
4. Fit the selected pipeline on the complete training partition.
5. Evaluate it once on the held-out test partition with MAE, RMSE, and R².
6. Save predictions and calculate permutation importance on the held-out test data.

### How to explain the metrics

- **MAE:** Average absolute difference between estimated and actual grades; lower is better.
- **RMSE:** Error measure that emphasizes larger misses; lower is better.
- **R²:** Fraction of held-out target variation explained relative to a mean-prediction baseline; interpret carefully, especially on a small dataset.
- **Permutation importance:** How much held-out MAE worsens when a feature is randomly shuffled. It indicates model reliance, not causality.

## 7. Dashboard demonstration script

1. Start the app with `streamlit run app.py`.
2. Open **Overview** and explain the data-to-support workflow.
3. Open **Explore data** and discuss the EDA charts without causal claims.
4. Open **Model performance** and explain that only the latest local run supplies metrics.
5. Open **Support prediction**, enter an illustrative record, and discuss the output as a conversation prompt.
6. Open **Limitations** to demonstrate awareness of privacy, fairness, leakage, timing, and external validation.

## 8. Suggested portfolio talking points

- “I built a reproducible pipeline from data collection to an interactive dashboard.”
- “I prevented an obvious grade-leakage issue by excluding prior period grades from the early-intervention model.”
- “I compared multiple regression models with cross-validation instead of choosing a model by intuition.”
- “I used a final held-out split and permutation importance to make the evaluation and explanation more credible.”
- “I designed the dashboard as decision support with safeguards, not as an automated student-evaluation tool.”

## 9. Limitations to say explicitly

- This source is a small historical dataset from two schools and may not transfer elsewhere.
- Some variables can change over a term; their availability must be controlled by a timestamped intervention workflow.
- The source is observational; model results do not establish causes.
- Support thresholds are project assumptions, not validated institutional policy.
- Real use needs approval, privacy protection, fairness assessment, monitoring, and validation on local data.
